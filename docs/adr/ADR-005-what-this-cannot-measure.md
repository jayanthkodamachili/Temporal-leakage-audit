# ADR-005: what this repository deliberately cannot measure

## Status

Accepted. This is the boundary record, so the limits are a decision rather than an
oversight.

## Context

The audit produces a confident list of named violations in two seconds with no data. That
confidence is earned in one narrow sense and not in several others, and a reader who takes
the list for more than it is will trust a clean audit further than it deserves.

## Decision

Five things are out of scope, each for a stated reason, and the README carries them in a
section of its own rather than in a footnote.

## What is out of scope, and why

**What a violation is worth.** This is the sharpest limitation and the one experiment two
exists to expose. Of four violations in the example pipeline, one accounted for essentially
all of the inflation and the other three for none, because legitimate features already
carried the same signal. The audit ranks by severity, and severity is not consequence.
Anyone using the violation list as a work queue is using it for something it cannot do.

**Whether the declared metadata is true.** The audit reads what a feature says about
itself. A window declared as trailing and implemented as centred audits clean, and the
implementation is simply not the thing being read. Closing that gap means parsing the
transformation code or diffing a recomputed column against the stored one, which is the
Pivot.

**Rule completeness.** Experiment four reports perfect recall, on leaks generated by
violating the same conditions the audit checks. That demonstrates the implementation is
correct against its rules across thousands of randomly shaped pipelines. It demonstrates
nothing about whether the rules cover every way a value can arrive too early, and a leak
of an unmodelled kind would be scored as a success by that experiment.

**Entity-level leakage.** Everything here concerns the time axis. A duplicated key putting
one row in both train and test, or an identifier that encodes the outcome, is a real and
common failure that this does not look for and would report as clean.

**Real data.** The panels are synthetic, with a target depending on two lags of one series.
The mechanism is structural and transfers; the magnitudes are properties of the generator.

## Observed against declared

Everything in `docs/metrics.json` is observed: produced by code here, re-run by CI. One
thing is declared rather than observed and should be read as a modelling assumption, that
this panel's dependence structure resembles a production forecasting problem in any respect
that matters.

## A perfect score is a claim about a narrow thing

Recall and precision of one, over 7595 injected leaks, is reported with its interpretation
attached in the same paragraph rather than left to stand alone. The resolution limit is not
the sample size here; it is that the generator and the audit share a definition of what
counts as a leak. No larger trial count would change that, which is why the experiment says
so in its own docstring rather than only in this file.

## Machine dependence

The published figures are r2 scores, counts and ratios, all machine independent. No
duration is published as a headline. The audit's runtime is a selling point and is
described in words rather than as a measured number, because a measured number there would
be a fact about the runner.

## Consequences

The repository makes a narrower claim than its numbers would support if read carelessly,
and says so in the most prominent place a limitation can go. A reviewer who reads this file
first should find nothing in the README that overreaches it.
